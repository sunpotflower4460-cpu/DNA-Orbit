## Decision ID

`ADR-005`

## 日付

## 状態

## 題名

Bass Anchor(Linkwitz-Riley 4次クロスオーバー)の実装と、CPU最適化(§11)のスコープ決定

## 背景

仕様書§4は、低域(キック・ベース)が軌道のパン/ディレイ/バックゲインに
巻き込まれることで中心が不安定になる、という問題を指摘している。
Bass Anchorは、設定周波数以下を軌道から外し、元の定位のまま直接出力へ
残すことでこれを解決する。

## 設計

```
入力L/R
  ├─ Linkwitz-Riley 4次クロスオーバー(チャンネルごと)
  │    ├─ 低域 → 直接Wetへ加算(パン/ディレイ非適用、元の定位のまま)
  │    └─ 高域 → Mid/Side導出・Strand/Core/Stereo Preserve bedの入力に
  └─ Dry: 常に無加工の元信号(低域・高域とも)
```

- **フィルタ**: `juce::dsp::IIR::Filter`によるButterworth(Q=1/√2)2次
  フィルタを低域・高域それぞれ2段カスケードし、LR4を構成
  (`Source/dsp/CrossoverFilter.h`)。JUCEの実装済みbiquadを再利用し、
  自前でbiquadを実装するリスクを避けた。
- **再合成のフラットさ**: LR4は低域+高域が振幅・位相ともフラットに
  再合成される(理論上、極性反転は不要)という性質を持つが、これを
  仮定せず`Tests/CrossoverFilterTests.cpp`で20Hz〜20kHzスイープの
  実測により検証した(全帯域で±0.5dB以内)。極性反転が必要だった場合は
  このテストが失敗して発覚する設計にした。
- **低域の扱い**: 低域はStrand/Core/Stereo Preserve bedと同じ扱いで
  Wetへ直接加算する(パン中央固定・ディレイなし)。「元のL/Rまたは
  M/Sを保持」という仕様書の要求どおり、クロスオーバー処理以外の
  加工を一切行わない。
- **モノラル安全性**: Stereo Preserve bedとは異なり、低域はモノ和で
  必ず打ち消し合う保証はない(入力の低域が元々持っていたステレオ特性を
  そのまま反映するため)。これは仕様どおりであり、入力自体より
  モノ互換性を悪化させることはない(悪化させるとしたら入力の低域が
  そもそも位相問題を抱えている場合のみ)。
- **Off(バイパス)の定義**: パラメータ範囲の最小値20Hzを、単なる
  「ほぼ効果がない値」ではなく、DSPコード上の**完全バイパス分岐**
  として実装した(`bassAnchorBypassed`)。これにより:
  - UI表示上の"Off"と、実際のDSP動作の"Off"が完全に一致する。
  - schema 2以前(Bass Anchor登場前)のプロジェクトを20Hzへ強制
    することで、既存プロジェクトの音を数式レベルで完全に再現できる
    (クロスオーバー自体が一切実行されないため、20Hz HPFによる
    位相回転すら発生しない)。
- **Auto Gain**: 低域の寄与は(Stereo Preserve bedと同様の理由で)
  既存の幾何ベースWet Makeup予測式に含めない。低域のパワーは入力の
  実際の低域エネルギー量という信号依存量であり、これを予測に含めると
  信号適応型になりポンピングのリスクを持ち込む。

## CPU最適化(仕様書§11)のスコープ決定

仕様書§11は次を提案している: (a) フィルタ係数・coherence推定・Auto
Level・Characterマッピングを8〜16サンプル単位のControl Rateへ、
(b) 対称ロック時の`sin(θ+π)=-sin(θ)`等による三角関数の重複回避、
(c) Mixゲインの制御レート化、(d) `fmod`を位相超過時のみ実行。

今回のPhase 3では次の判断をした:

- **採用**: 新規追加したBass Anchorのフィルタ係数更新をブロック単位
  (1ブロックにつき最大2回、L/Rそれぞれ)に限定した
  (`HelixEngine::applyParameters`内、`CrossoverFilter::setCrossoverHz`
  自体も値が変わらなければ即returnする防御を持つ)。Butterworth係数の
  計算は`sin`/`cos`を複数回含み、サンプル単位で行うには重すぎるため、
  新規コードは最初からControl Rateで書いた。
- **見送り**: 既存の`sin(thetaA)`/`sin(thetaB)`等の重複計算回避、
  Mixゲインの制御レート化、`fmod`の条件付き実行は、**今回は実装しない**。
  理由:
  1. これらは全て既存の、大量のテストで固定された挙動に対する
     最適化であり、僅かな数値差(sin/cosの計算順序変更、浮動小数点の
     丸め)が`Tests/BaselineRegressionTests.cpp`のフィンガープリントや
     他の既存テストの許容誤差を超える形で影響する可能性がある。
     慎重な差分測定なしに広範囲へ手を入れるのは、"don't disrupt
     existing project sound more than necessary" という制約に反する。
  2. この環境(コンテナ、オーディオデバイスなし)では実際のCPU負荷を
     信頼性高く測定できない。仕様書§11.3自身も「絶対数値は実機依存の
     ため、CIでは前版比の回帰検出を重視する」と述べており、CI
     (GitHub Actions)を使わない本プロジェクトの方針からも、
     この種の最適化の効果を定量的に確認する手段が今はない。
  3. 現時点でCPU負荷が実際に問題になっているという実測データがない
     (最適化対象が「推測」の状態)。
  - **再検討条件**: 実DAWでの複数インスタンス使用時にCPU負荷が
    問題になった場合、または信頼できるベンチマーク環境が用意できた
    場合に、個々の最適化を「変更前後でBaselineRegressionTestsが
    通ることを条件に」1つずつ導入する。まとめて一度に変更しない。

## 決定

上記の設計を採用。CPU最適化は新規コード(Bass Anchor)のみ
Control Rateで実装し、既存コードの最適化は実測データが揃うまで見送る。

## 理由

- 音質: 低域を軌道から切り離すことで、指摘された「低域の不安定さ」を
  解消する。既存のPhase 2.5と同じ「信号適応にしない」原則を維持。
- 互換性: 20Hz(Off)が真のバイパスであるため、schema 2以前の
  プロジェクトは数式レベルで無変更。
- 実装難度・テスト可能性: JUCEの`dsp::IIR::Filter`を再利用し、
  自前biquad実装のリスクを回避。再合成フラットネスを実測で検証。

## 影響

### 良い影響

- 低域が軌道の影響を受けなくなり、キック/ベースの中心が安定する。
- 既存プロジェクトの互換性は完全に保たれる。

### 悪い影響

- 新しいIIRフィルタ(チャンネルあたり4段)が常時(Bass Anchorが
  Offでない限り)動作するため、わずかにCPU負荷が増える。ブロック単位の
  係数更新により、サンプル単位更新よりは軽い。

### 互換性

- 新規パラメータID `bassAnchorHz` 追加。既存パラメータIDは変更なし。
- state schema version 3に更新。schema 2以前の保存データは
  `bassAnchorHz`ノードが存在しないため、ロード時に20Hz(Off)へ
  強制される。
