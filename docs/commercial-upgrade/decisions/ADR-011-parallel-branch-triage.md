## 決定1: static-realtime-audit.sh を採用する(ただし改良が必須だった)

オーディオスレッド上の禁止事項(ヒープ確保・ロック・ファイルI/O・
メッセージスレッド呼び出し)を静的に検出するスクリプト。設計思想が
正しく、特に自らの限界を明記している点(「A clean scan is not proof of
real-time safety」)、コアDSPはFAIL・Processorファイルは正当な
非コールバックコードがあるためWARN、という階層分けが妥当だった。

**ただし現状のままでは使い物にならなかった。** 自分のコードベースに
対して実行したところ、4件のFAILが報告されたが**すべてコメント内の
誤検出**だった:

- `HelixEngine.h:118` 「HelixEngine stays **free** of」
- `HelixEngine.h:341,347` 「lock-**free**」×2
- `OrbitMath.h:7` 「JUCE-**free** math helpers」

正規表現`(new|delete|malloc|calloc|realloc|free)[[:space:](\[]`が散文の
`free `にマッチしていた。本プロジェクトは意図的にコメントが厚いため、
このままでは狼少年になり、遠からず誰もスクリプトを実行しなくなる。

採用にあたり次を改良した:

1. **コメント除去**: awkで`//`と`/* */`の内容を行番号を保ったまま空白化
   してから走査する。
2. **パターンの厳密化**: `malloc(`のように呼び出し構文を要求し、
   `new Type`のように型を伴う形のみを検出する。コメント除去が
   文字列リテラルで破られた場合の二重の防御。
3. **`std::vector`/`std::function`/`std::string`等のWARN追加**:
   確保を隠しうる間接参照を定期的に見直すため。
4. **`M_PI`のWARN維持**: 本プロジェクトはPhase 0で意図的に除去済み
   (`orbitmath::pi`へ)なので、再出現は移植性の後退。

### 実際に検証した(PR #2が未実行だった negative test を含む)

- 改良後の現行コードに対して: **0 failure**、WARNは
  `createEditor()`の`new DNAOrbitAudioProcessorEditor`など
  すべて正当なメッセージスレッド側のコードのみ。
- **静かなだけではないことの証明**: `HelixEngine::process()`に
  意図的に4種の危険(`new float[64]`、`std::vector`、
  `std::mutex`+`lock_guard`、`printf`)を注入して実行したところ、
  FAIL 3グループ(確保・ロック・ログ)+WARN(間接参照)を検出し、
  終了コード1でブロックした。注入は検証後に完全に復元済み
  (`git status`で確認)。

## 決定2: BenchmarkDSP.cpp を採用する

決定論的なスループット測定ツール。計測前に100ブロックのウォームアップ、
複数のサンプルレート/ブロックサイズ/インスタンス数、ns/sampleと
%realtimeの両方で正規化、という方法論が妥当だった。

ADR-005では「このコンテナは信頼できるCPU測定値を出せない」ことを理由に
仕様書§11の広範なCPU最適化を保留した。それは今も変わらず、このツールも
**絶対値は無意味**である。しかし**同一マシン・同一セッションでの
変更前後の相対比較**には使えるので、ADR-005が「測定手段がまったく無い」
として保留していた状態からは前進する。その旨をファイル冒頭に明記した。

実行結果(このコンテナ、参考値): 全構成で約240 ns/sample/instanceと
一貫しており、小ブロックサイズや高サンプルレートで破綻しないことは
確認できた。

## 決定3: 書類ガバナンス層(57ファイル)を採用しない

`docs/governance/PRODUCT_CONSTITUTION.md`(SHA-256ロックされた10本の柱)、
R0〜R4リスクモデル、G0〜G6ライフサイクル、パスごとの変更記録、
例外レジストリ(ISO期限付き)、リリース判断ログ、
`scripts/quality-governance-audit.py`(432行)、`.claude/`配下のrules/
agents/skills、`AGENTS.md`/`CONTRIBUTING.md`/PRテンプレート。

監査スクリプトの中身を実際に読んだ結果、それが検証しているのは
**「変更したパスごとに、対応するmarkdownの変更記録が、正しい見出しと
リスク階層付きで存在するか」という書類の突合**であり、コードの正しさ・
音質・リアルタイム安全性・音量の妥当性は一切検証していない。

不採用の理由:

1. **本プロジェクトは既に、より強い形で同じ目的を達成している。**
   ガバナンスが目指す「保証を黙って弱めない」「検証していないことを
   検証済みと書かない」は、本プロジェクトでは**書類ではなく自己強制的な
   仕組み**で実現している:
   - 保証はテストで固定される(111スイート)。弱めれば書類レビューを
     待たずにテストが落ちる。実例として、今回のADR-010では
     `PresetIntensityTests.cpp`が「プリセットが可聴であること」を
     数値で固定した。
   - 検証済み/未検証の境界は`MANUAL_REQUIRED.md`が担う。
   - 本当に判断があった箇所にのみADRを書く(現在11本)。ゲートに
     要求されたから書くのではない。
   - `Tools/local_validate.sh`がRelease+CTest、ASan/UBSan、-Werror、
     clang-tidy、そして今回追加のrealtime auditを自動実行する。
2. **規模が不釣り合い。** オーナー1人+エージェントという体制に対し、
   コードを1行触るたびにリスク階層宣言・グロブパターン・独立レビュー
   記録を伴う変更記録の作成を必須にする運用は、規制産業の複数チーム
   向けの重さである。形骸化して迂回されるのが最も可能性の高い結末で、
   その状態は「ガバナンスが無い」より悪い(あるという錯覚を生むため)。
3. **未実行のまま。** PR #2自身が監査スクリプトの自己テストすら
   実行できていないと明記している。57ファイルの未検証な運用機構を
   取り込むことは、本プロジェクトが一貫して守ってきた
   「実行していない検証を確認済みと書かない」という原則に反する。
4. **憲章の承認はオーナーの専権事項。** PR #2自身が
   「product-owner approval remains intentionally PENDING」と
   記している。エージェントの判断で採択すべきものではない。

なお、ガバナンス文書が掲げる価値観そのもの(P3物理的誠実さ、
P8視覚と言葉の真実、P9確信より証拠、P10可逆性)には賛同する。
本プロジェクトのADR群・テスト・`MANUAL_REQUIRED.md`は、すでに
同じ価値観を、より軽い手段で実装している。

## 決定4: DSP/UIの再実装とテストを採用しない

Stereo Preserve bed、Bass Anchor(Linkwitz-Riley)、Character、
Host Lock、Soft Bypass、相関考慮Mix — PR #2が実装しているものは、
本ブランチがADR-004〜ADR-009として**実測・テスト・サニタイザ検証済みで
既に実装している機能と完全に重複**する。

決定的な差は検証状態にある。本ブランチの実装は111スイートのCTestと
ASan/UBSanをクリアしているのに対し、PR #2の実装は本人の記述どおり
一度もコンパイルされていない。2つの設計をmainで混在させることは
できず、検証済みの側を残すのが妥当。

PR #2側のテスト(`StereoCenterTests`、`MusicalDspTests`、
`CommercialParameterStateTests`等)も、そのブランチのエンジン挙動に
対して書かれているため、そのままでは本実装に適用できない。カバー範囲は
本ブランチの既存テストが実質的に包含している(例: エネルギー加重中心の
検証は`StereoPreserveTests.cpp`が閉形式の予測値で行っている)。

## 影響

### 良い影響

- オーディオスレッド安全性の後退を、テストでは捕捉できない形で
  検出する自動チェックが加わった(しかも誤検出なしで、かつ本物の
  危険を検出できることを実証済み)。
- CPU最適化の判断材料(相対比較)が初めて手に入った。
- 並行ブランチの成果のうち価値ある部分が失われずに残った。

### 悪い影響

- PR #2の作業の大部分は採用されない。ただしブランチ自体は
  リポジトリに残るため、将来ガバナンス体制が必要になった場合
  (チーム化、外部監査要件の発生など)は参照できる。

### 互換性

- パラメータID・schema・音への影響は一切なし。追加されたのは
  ビルド対象外の開発ツール2点とCMakeのオプションターゲットのみ。
