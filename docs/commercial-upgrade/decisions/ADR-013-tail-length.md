# DNA Orbit 意思決定ログ

## Decision ID

`ADR-013`

## 日付

2026-08-03

## 状態

- Accepted

## 題名

`getTailLengthSeconds()` を 0.05 から 0.1 へ修正する
(Bass Anchor 導入でテール申告が過少になっていた実バグ)

## 背景

整合性の全体監査の一環として、内部のディレイ予算とホストへの申告値を
突き合わせた。`HelixEngine::prepare()` のコメントは「最大 back-delay
14ms(Character=Deep)+ 最大 Twist 20ms = 34ms、60ms を確保」と
書いているのに対し、`getTailLengthSeconds()` は 0.05(50ms)を
返していた。50ms > 34ms なので純ディレイは収まっているが、
0.05 という値は Character 導入前(back-delay が 8ms 固定 = 合計 28ms)
に決められたまま、その後の変更で再検討されていなかった。

## 問題

テールは純ディレイだけではない。`getTailLengthSeconds()` はホストが
**オフラインバウンス・フリーズ時に、入力終了後どれだけ音を引き続き
取り出すか**を決めるために使う値であり、フィルタのリンギングを含む
「実際に音が鳴り続ける時間」でなければならない。過少申告すると
テールが切り落とされる。

推測で直さず、実際のエンジンで測定するテスト
(`Tests/TailLengthTests.cpp`)を追加した。入力を無音にした後、
出力が入力ピークに対し -60dBFS を下回り続けるまでの時間を測る。

初回の測定(Character=Deep + Twist最大 + Bass Anchor 既定120Hz):

| サンプルレート | 実測テール | 申告値 |
|---|---:|---:|
| 44.1kHz | 34.81ms | 50ms |
| 48kHz | 31.75ms | 50ms |
| 96kHz | 38.66ms | 50ms |
| 192kHz | 41.83ms | 50ms |

ここまでは収まっており、当初の疑いは外れだった。しかし**真の最悪ケースは
最長ディレイではなく、作動する最低クロスオーバー周波数**である。
4次 Linkwitz-Riley は遮断周波数が低いほど長くリンギングする。
`bassAnchorHz` の下限は 20Hz だが、20Hz は専用のバイパス分岐に入るため
クロスオーバーは動かない。**20Hz を僅かに超えた値(21Hz)が実際に
作動する最低周波数**で、ここを測ると:

| サンプルレート | 実測テール(21Hz) | 申告値 |
|---|---:|---:|
| 44.1kHz | **73.22ms** | 50ms |
| 48kHz | **68.38ms** | 50ms |
| 96kHz | **72.08ms** | 50ms |
| 192kHz | **70.65ms** | 50ms |

4サンプルレートすべてで申告値を超過。実害は、Bass Anchor を下限付近に
設定した状態でオフラインバウンスすると、ホストが 50ms で打ち切るため
**約 20ms のテールが切り落とされる**こと。

## 決定

`getTailLengthSeconds()` を **0.1(100ms)** に変更する。
実測最悪値 73.22ms に対し約 27ms の余裕を持つ。

`Tests/TailLengthTests.cpp` がこの関係を固定するので、将来
Character にさらに長いディレイを足す、Bass Anchor の下限を下げる等の
変更で実テールが申告値を超えた場合、テストが落ちる。

## 「閾値を緩めただけの修正」ではない

ロードマップの変更禁止事項には「閾値を緩めるだけの修正」がある。
本件は表面的にそれに似ているため、区別を明記しておく。

`getTailLengthSeconds()` は**品質のハードルではなく、ホストに対する
事実の申告**である。「このプラグインは入力終了後これだけ鳴り続ける」
という宣言であり、実測がそれを超えているなら宣言のほうが誤っている。
値を上げることは基準を緩めることではなく、**誤った申告を実態に
合わせて正すこと**である。逆に値を下げてテストを通すのが、
禁止されている「閾値を緩めるだけの修正」に当たる。

代償もない: ホストがバウンス時に 50ms 余分に音を引き出すだけで、
音質・CPU・互換性のいずれにも影響しない。

## 理由

- 正しさ: ホストへの申告が実測と一致するようになる。
- 検証可能性: 推測ではなく実測で決めた値であり、その測定自体が
  テストとして残るため、将来の変更で再発しない。
- リスク: なし(申告を長くする方向は安全側)。

## 影響

### 良い影響

- Bass Anchor を下限付近に設定した状態でのオフラインバウンス・
  フリーズでテールが切れなくなる。
- テール長と実装の関係が初めてテストで固定された。

### 悪い影響

- ホストがバウンス時に最大 50ms 余分に処理する(無視できる)。

### 互換性

- パラメータID・schema・音の内容に影響なし。ホストへ申告する
  メタデータのみの変更。

## 実装

- file: `Source/PluginProcessor.h`(`getTailLengthSeconds()` を
  0.05 → 0.1、経緯をコメントで明記)

## テスト

- unit: `Tests/TailLengthTests.cpp`(既定 Bass Anchor での最悪ケース、
  作動する最低クロスオーバー 21Hz での最悪ケース、Bass Anchor Off、
  いずれも 44.1/48/96/192kHz で申告値に収まることを検証)
- 全115件のCTest + ASan/UBSan がクリーン

## 再検討条件

Character にさらに長い back-delay を追加する、`bassAnchorMinHz` を
下げる、あるいは新たな残響系処理を追加する場合、
`Tests/TailLengthTests.cpp` が自動的に失敗するので、その時点で
申告値を再測定して更新する。
